## Хранилище

Модуль app/audio_storage.py не импортирует модели БД и не обращается к STT.
Один локальный постоянный том, общий для API и worker. Каталог вне static.
API пишет, worker только читает. Временные файлы находятся на том же томе.

Предлагаемый Python-интерфейс

```python
@dataclass(frozen=True)
class AudioInfo:
    sha256: str
    byte_count: int
    duration_seconds: float
    media_type: str

@dataclass(frozen=True)
class StoredAudio:
    key: str
    info: AudioInfo

class AudioStorage:
    def stage(self, source: BinaryIO) -> ContextManager[StagedAudio]: ...
    def inspect(self, staged: StagedAudio) -> AudioInfo: ...
    def publish(self, staged: StagedAudio, capture_id: str, info: AudioInfo) -> StoredAudio: ...
    def open_original(self, key: str) -> ContextManager[BinaryIO]: ...
```

stage читает поток порциями, считает SHA-256 и фактический размер. Пустой файл отклоняется. Максимум 10 * 1024 * 1024 байт включительно. Заголовки и имя файла не определяют формат. Контекст удаляет только свой временный файл.

inspect проверяет контейнер, единственный аудиопоток и полное декодирование. Длительность определяется по декодированным сэмплам, не только по метаданным. Допускается 0 < duration <= 180 секунд. Предлагаемый первый набор форматов — Ogg/Opus для голосовых Telegram и WAV/PCM для веба. Поддержка других форматов требует явного согласования; это предложение, а не уже утверждённое ограничение MVP.

Для проверки предлагаем ffprobe и ffmpeg отдельными процессами без shell. Только локальный файл, запрет сетевых протоколов и плейлистов, ограничение времени, памяти, потоков и объёма декодированного вывода. При превышении лимита процесс прекращается. Ошибки декодера и пути не возвращаются пользователю. На текущем Mac этих инструментов нет, проверка настоящего декодера ещё не выполнялась. Версию и системную установку согласуем с образом API и CI; Python multipart-зависимость фиксирует Марк.

publish сохраняет точные исходные байты без перекодирования. Имя создаётся сервером по UUID Capture, ключ не содержит пользовательских путей. Файл создаётся без перезаписи существующего объекта. До возврата выполняются fsync файла и каталога. Каталог закрыт, файлы не доступны всем пользователям системы. Ссылки и выход за пределы каталога запрещены.

open_original принимает только валидный внутренний ключ. Проверка владельца выполняется вызывающим маршрутом до открытия файла. Worker получает ключ только из Capture, не из запроса пользователя. Никаких публичных URL и загрузки по произвольному адресу.

Исключения модуля — AudioTooLarge, UnsupportedAudio и AudioStorageUnavailable. Последнее включает сбои диска и недоступный декодер, но не раскрывает содержимое исключения. Модуль не принимает HTTP-решений и не удаляет оригинал после ошибки STT.

## Приём и транзакция

В app/routes/audio.py предлагаем фабрику

```python
build_router(database, settings, storage, create_audio_capture) -> APIRouter
```

Марк подключает фабрику и предоставляет функцию ядра

```python
create_audio_capture(
    db, *, capture_id, user_id, idempotency_key, stored_audio, channel, settings
) -> Job
```

Функция создаёт Capture и Job в переданной транзакции, проверяет очередь/квоту, фиксирует событие, но не вызывает commit и не обращается к STT. Capture.id равен переданному capture_id, Job.capture_id ссылается на него. Поля Capture — input_kind=audio, processing_mode=ai, audio_key/seconds/bytes из StoredAudio, transcript=NULL. Предлагаем original_text="" до STT, без выдуманной расшифровки; дальнейшее хранение и версии расшифровки согласует Марк. Worker обязан различать text и audio до отправки в LLM.

Рабочий endpoint — POST /internal/v1/telegram/voice. Multipart-поля и TelegramCaptureResponse уже определены общим контрактом. Обработка допускает одно поле audio и по одному значению каждого служебного поля; неоднозначные и лишние поля отклоняются. Сервисная авторизация проверяется до чтения и декодирования файла. После проверки размера считаем digest из всех служебных полей, вида операции voice и SHA-256 оригинальных байтов. Имя файла и заявленный MIME не входят в идентичность записи.

Используем существующие process_update и telegram_identity из app/routes/internal.py. Для process_update внутренняя модель тела содержит audio_sha256 вместе с Telegram ID и processing_mode. Это сохраняет единую уникальность (bot_id, update_id) между текстом, голосом, привязкой и кнопками. Изменять функцию process_update без согласования не будем.

Порядок внутри handler после резервирования Inbox

1. Определить владельца через подтверждённую TelegramIdentity.
2. Проверить реальный формат и длительность временного файла.
3. Сгенерировать Capture UUID, устойчиво опубликовать оригинал.
4. Вызвать create_audio_capture без commit и вернуть ответ сохранения.
5. process_update фиксирует Inbox, Capture, Job и событие одной транзакцией. Только после этого вернуть saved.

Точный повтор возвращает прежний результат без повторного декодирования, создания Capture и задания STT. При том же update ID и других байтах возвращается 409 conflict. Конкурентные повторы проверяются на PostgreSQL.

Превышение размера или длительности — 413 input_too_large. Неподдерживаемый, пустой или повреждённый файл — 400 unsupported_audio. Ошибки схемы — 422 invalid_input. Неисправность хранилища/декодера — временный 503 unavailable без сохранения окончательного отказа. После открытия Inbox бизнес-отказ сохраняется существующим process_update; ранний отказ при потоковом превышении размера не обязан создавать Inbox.

Файловая система и БД не образуют общей транзакции. При rollback или неизвестном результате commit опубликованный файл не удаляется немедленно. Иначе можно удалить оригинал уже принятой записи. Допустим временный файл без ссылки в БД; недопустима успешная запись в БД до устойчивого сохранения файла. Очистка таких объектов должна сверяться с БД, исключать активные загрузки и иметь запас по времени. Автоматический сборщик до отдельной проверки не запускаем, объём диска контролируем. Резервная копия включает БД и аудиотом.

## Доступ к оригиналу и подключение

Предлагаем GET /api/v1/captures/{capture_id}/audio в том же модуле. Проверка браузерной сессии и владельца, чужой или отсутствующий Capture возвращает 404. Ответ attachment, Cache-Control: no-store, X-Content-Type-Options: nosniff. Путь/ключ хранилища в ответ не включается. Ошибка STT не закрывает доступ к файлу. Публичный маршрут загрузки аудио из веба пока не согласован; его контракт потребуется отдельно, чтобы веб-голос не потерялся из MVP.

Марк добавляет настройки пути хранилища и декодера, создаёт storage при старте API, подключает router и передаёт read-only storage в worker. Наш модуль не подключает себя в main.py и не меняет зависимости. В API и worker при интеграции проверить пользователя ОС и права общего тома. Формат передачи байтов в STT выбирает Марк; оригинал на диске остаётся неизменным.

## Проверки перед приёмкой

- Реальные синтетические Ogg/Opus и WAV/PCM, поддельный MIME, повреждённый и обрезанный файл, файл без аудио и с несколькими потоками.
- Размер ровно 10 МиБ и превышение на байт; chunked без достоверного Content-Length; длительность ровно 180 секунд и превышение по сэмплам.
- Таймаут/отсутствие декодера, недоступный диск, ошибка fsync; никакого saved до устойчивого файла и commit БД.
- Точный и изменённый повтор, конкуренция на PostgreSQL, конфликт ID между voice и text; остановка адаптера на конфликте без продвижения offset.
- Сбой и неизвестный commit, повтор после рестарта; единственный Capture/Job, сохранность оригинала, отсутствие обработки STT в HTTP-запросе.
- Чужой аккаунт, неподтверждённый Telegram, неверный сервисный ключ, traversal/symlink; отсутствие секретов и содержимого в логах.
- Ошибка mock STT сохраняет оригинал; владелец скачивает те же байты, другой пользователь не получает их. Настоящий Cloud.ru не вызывается.

Для начала реализации Марку достаточно подтвердить фабрику router, функцию create_audio_capture, интерфейс storage, начальные форматы и маршрут скачивания либо перечислить изменения. Это согласование технического контракта, покупки и развёртывание сейчас не требуются.
