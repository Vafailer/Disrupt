# Совместная разработка: основатель и Марк

Оба разработчика используют Codex на разных компьютерах. Локальные файлы и коммиты другому участнику не видны: перед передачей результата отправлять рабочую ветку в origin и давать ссылку на конкретный коммит. Не считать договоренность принятой другим участником только потому, что документ появился в нашей ветке.

## Границы изменений

| Ответственный | Файлы и задачи |
|---|---|
| Основатель + Codex | `telegram_adapter/`, `tests/telegram_adapter/`, `deploy/Dockerfile.telegram`, `deploy/compose.telegram.yaml`, `docs/telegram-*.md`; далее `app/scheduler.py`, `app/audio_storage.py`, `app/routes/audio.py`, `app/static/admin.*` и тесты этих модулей |
| Марк + Codex | Модели, схемы и все миграции; авторизация; внутренние Telegram-маршруты; STT/LLM worker; основной веб; события и API бизнес-статистики |
| Марк интегрирует | `app/main.py`, общие зависимости и lock-файлы, общие настройки приложения |
| По согласованию отдельным изменением | Общие Dockerfile/Compose/Caddy, CI, `AGENTS.md`, общий API-контракт и пересекающиеся тесты |

Аудиомодуль и маршрут пишет основатель по моделям Марка; подключение маршрута в приложение делает Марк. Изменения инфраструктуры готовит основатель, перед правкой общих файлов согласует их с Марком. Не создавать параллельные миграции, второй Telegram-адаптер или альтернативную реализацию одного маршрута. Нужное изменение чужого файла описать в своем PR и передать владельцу.

## Ветки и передача контракта

1. Наша ветка — `codex/telegram-adapter`. Ветка Марка — `feature/integration-v1-core`; не менять ее. Совместная проверка идет в `integration/telegram-core-v1`. Каждый работает в своей ветке, без прямых push в main и без force-push общей истории.
2. Перед началом работы выполнять `git fetch origin`, проверять свою ветку и незакоммиченные изменения. Не переключать ветки с незавершенными правками и не использовать reset/clean для устранения конфликтов.
3. Марку передать этот файл и `docs/telegram-adapter.md` из нашей опубликованной ветки. Его Codex должен прочитать их до изменения Telegram API и закрепить согласованные правила в своей ветке. До этого документ не обеспечивает координацию автоматически.
4. `docs/telegram-adapter.md` описывает реализованный клиент, а не готовый сервер. Марк фиксирует согласованный OpenAPI в `docs/integration-v1.yaml` и эталонные запросы/ответы в `docs/integration-v1-examples.json`. Эти файлы включены в интеграционную ветку и генерируются скриптом `scripts/export_contract.py`. Несовпадения сначала согласовать, затем менять клиент и сервер; не подгонять их независимо.
5. До разработки админки Марк фиксирует формат агрегатов и ошибки доступа. До scheduler — модели доставки, lease/generation и операции claim/authorize/result. Отсутствующие контракты не заменять догадками о сервере.

## Объединение

Отправлять небольшие законченные коммиты в свою ветку. В PR указывать изменения, проверки и зависимости от другой ветки. Перед объединением просмотреть diff обеих веток относительно main и пересечение файлов; разрешать конфликты по смыслу, без автоматического выбора ours/theirs.

Проверять совмещенный код в отдельной интеграционной ветке: тесты и линтер, миграции на тестовой PostgreSQL, затем связку API и бота с mock-моделью. Проверить повтор Telegram update, сохранение исходника до ответа, запрет чужого доступа и подтверждение привязки. Добавление scheduler/админки требует проверки их сценариев. Зеленые изолированные тесты адаптера не подтверждают готовность общей системы.

Объединять в main через проверенный PR. При недоступности ветки другого участника прямо указывать, что отсутствие конфликтов и совместимость еще не проверены. Агенты не используют выданный команде токен Cloud.ru; секреты и личные записи в Git не добавлять.
