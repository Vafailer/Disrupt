# Напоминания и доставка v1

Ветка `feature/reminder-core-v1` создана от нашего ядра `80002342180fb07ea3c95eca594f3b7c7ff2a82f`. На том этапе scheduler и отправка оставались за коллегой. В `feature/reminder-delivery-v1` они реализованы по этому контракту, есть [инструкция подключения](telegram-delivery-v1.md). Формы напоминаний в основном вебе пока нет. Живую доставку ещё нужно проверить.

## Напоминания пользователя

Все методы требуют браузерной сессии. Для POST и PATCH нужен `X-CSRF-Token`, проверяется Origin. Владелец берётся из сессии. Чужая запись, задача или напоминание возвращает 404.

| Метод | Действие |
|---|---|
| GET /api/v1/notes/{note_id}/reminders | Список с limit до 100 и offset |
| POST /api/v1/notes/{note_id}/reminders | Подтвердить новое напоминание |
| GET /api/v1/reminders/{id} | Текущее состояние |
| PATCH /api/v1/reminders/{id} | Изменить время, зону и текст |
| POST /api/v1/reminders/{id}/cancel | Отменить |

Создание требует `Idempotency-Key`, от 1 до 100 символов `[A-Za-z0-9_.:-]`. Пример тела без реальных данных.

```json
{
  "item_id": null,
  "scheduled_at": "2026-10-08T09:00:00Z",
  "timezone": "Europe/Moscow",
  "text": "Вернуться к заметке"
}
```

Время должно быть в будущем, ISO 8601 с Z или явным смещением. Значение без зоны и относительные сроки не принимаются. `timezone` является существующей зоной IANA и используется для отображения. Смещение времени не применяется второй раз. Ответ возвращает время в UTC.

Для напоминания по задаче передайте её `item_id`. Она должна быть открытой задачей этой же заметки и владельца. При null напоминание относится ко всей заметке. Текст от 1 до 1000 символов, без NUL и пустого содержимого. Наличие Telegram-связи не требуется для сохранения, но требуется перед отправкой. ИИ напоминания не создаёт.

Ответ 201 содержит id, note_id, item_id, scheduled_at, timezone, text, status, generation, confirmed_at, delivery_status и previous_attempt_unknown. Создание, событие `reminder_confirmed` и ключ повтора фиксируются одной транзакцией. Повтор того же тела возвращает то же напоминание в его текущем состоянии. Другое тело с тем же ключом даёт 409. Повтор после правки не отменяет эту правку.

Правка принимает scheduled_at, timezone, text и текущую generation. Связь с задачей не меняется. Устаревшая generation даёт 409. Новая редакция получает generation + 1 и статус confirmed.

Отмена принимает `{"generation": 1}`. Она увеличивает generation один раз. Повтор последней отмены не меняет запись. Выполнение задачи тоже отменяет её напоминания и старые разрешения доставки в своей транзакции.

`delivery_status` показывает Outbox текущего поколения либо null. `previous_attempt_unknown=true` означает, что для предыдущей редакции уже разрешили отправку и её результат неизвестен. Отмена или новая дата не позволяют обещать, что старое сообщение не придёт. Этот признак нужно показать пользователю рядом с подтверждением отмены или изменения.

## Что делает scheduler коллеги

Scheduler выбирает confirmed с наступившим scheduled_at. Проверяет владельца Note и Item, открытую задачу, актуальную generation и подтверждённую TelegramIdentity с notifications_enabled=true и delivery_status=available. Получатель берётся из этой связи, не из формы или модели ИИ.

Создаёт Outbox со статусом pending. Заполняет reminder_id, user_id, bot_id, chat_id и generation. Уникальность `(reminder_id, generation)` уже обеспечена БД. При конкуренции нужно принимать существующую строку, не создавать вторую. Перед проверкой и изменением данных владельца используйте `lock_account`; ядро соблюдает порядок account, затем Reminder/Outbox. Общие модели и миграции остаются с нашей стороны.

Scheduler не отправляет pending прямо в Telegram. Для отправки используются три рабочих метода `/internal/v1`. Они требуют отдельный сервисный Bearer. Формат запросов и ответов сохранился из общего контракта.

## Claim, authorize и result

`POST /deliveries/claim` получает bot_id и limit от 1 до 100. Возвращает items со следующими полями.

```json
{
  "delivery_id": "00000000-0000-4000-8000-000000000001",
  "lease_token": "ccccccccccccccccccccccccccccccccccccccccccc",
  "generation": 1,
  "chat_id": 123,
  "text": "Вернуться к задаче",
  "note_url": "https://example.invalid/?capture=00000000-0000-4000-8000-000000000002",
  "callback_token": "bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb"
}
```

Пустая очередь возвращает items=[]. Note-level напоминание получает callback_token=null. Ядро выдаёт оба токена с 256 битами случайности, хранит только хеши. Токен кнопки соответствует пределу Telegram в 64 байта. Не пишите токены, исходный текст и весь ответ claim в логи.

Claim не разрешает отправку. Перед каждой попыткой вызывается `POST /deliveries/{id}/authorize` с lease_token и generation. Только ответ send=true разрешает один вызов Telegram. Повтор authorize возвращает send=false. Перед разрешением снова проверяются срок lease, поколение, владелец, задача и получатель. Правка или отмена между claim и authorize блокирует старую отправку.

Lease по умолчанию 60 секунд. Он обновляется на полный срок при authorize. Настройка `NOTES_DELIVERY_LEASE_SECONDS` допускает от 30 до 300 секунд. Таймаут сетевой отправки должен укладываться в этот срок.

Если ответ authorize потерян, Telegram не вызывается по догадке. Если отправку ещё не разрешали, истёкший lease можно получить заново с новым токеном. После authorize истёкшая попытка становится unknown при следующем claim и автоматически больше не выдаётся.

`POST /deliveries/{id}/result` получает тот же lease_token, generation и результат. Пример успешного результата.

```json
{
  "lease_token": "ccccccccccccccccccccccccccccccccccccccccccc",
  "generation": 1,
  "status": "sent",
  "telegram_message_id": 123,
  "error_code": null,
  "retry_after_seconds": null
}
```

У sent обязателен message ID, поля ошибки равны null. У остальных статусов message ID равен null. Retryable требует retry_after_seconds от 0 до 86400; у blocked и unknown это поле равно null. Error_code содержит только короткий код `[a-z][a-z0-9_]*`, до 64 символов, без текста исключения или ответа Telegram.

Retryable допустим только при подтверждённом отказе без отправленного сообщения. После задержки claim выдаст новую попытку. Timeout или неизвестный исход обозначается unknown, без автоматического повторного сообщения. Blocked закрывает доставку этой Telegram-связи. Эти статусы нельзя подменять друг другом ради повтора.

Result возвращает status=recorded после commit. Точный повтор безопасен, другой результат для той же попытки даёт 409. Если ответ result потерян, повторяется этот же result, не отправка Telegram. После выдачи нового lease старый токен не принимает ни authorize, ни result.

Запоздалый result разрешён для ранее авторизованной попытки, в том числе после срока lease или отмены. Он сохраняет факт старой отправки, но не меняет новую generation напоминания. Кнопка завершения действует только для актуальной задачи и поколения. Время confirmed_at и события фиксируются ядром.

## Миграция и проверки

Миграция `9a16c3d80b24` идёт после `39e7b64d210a`. Она добавляет nullable idempotency_key и creation_hash в Reminder и уникальный индекс по владельцу и ключу. Старые напоминания и связанные Outbox сохраняются. Перестройки таблицы Reminder нет.

Проверки охватывают права, CSRF, время и зоны, повторы, неизвестный commit, поколения, отмену, блокировку получателя, срок lease, безопасный retry, поздний result и callback. На PostgreSQL отдельно проверяются конкурентное создание, claim, authorize, result и гонка с правкой расписания. Тесты используют вымышленные записи и не вызывают Telegram или Cloud.ru.

Для проверки из корня проекта выполните `python -m pytest -q` и `python -m ruff check app tests migrations scripts telegram_adapter`. Полный контракт обновляется командой `PYTHONPATH=. python scripts/export_contract.py`; три файла интеграции должны оставаться воспроизводимыми. В OpenAPI маршруты доставки теперь помечены implemented.
