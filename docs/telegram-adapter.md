# Telegram адаптер Beresta

Ветка `codex/telegram-adapter`. Реализованы входящие личные сообщения: `/start`, `/help`, `/save текст`, обычный текст, голос и callback выполнения задачи. Отдельный процесс на Python 3.12, без подключения к БД и без доступа к ключам модели.

**Статус:** транспорт проверен с `httpx.MockTransport`. Реальный Telegram и связка с ядром не проверены: маршруты ниже пока отсутствуют в исходном FastAPI. Scheduler, outbox-доставка, хранилище аудио ядра и админка в этот первый этап не входят. Наличие Dockerfile не означает проверку контейнерного запуска.

## Локальная проверка без секретов

Из корня репозитория:

```sh
.venv/bin/python -m telegram_adapter --demo
.venv/bin/python -m pytest tests/telegram_adapter -q
```

Демо не читает переменные с ключами, не обращается в сеть и использует фиктивное ядро. Проверяет принятие текста, подтверждение, сохранение offset и повтор одного update. Полный набор тестов: `.venv/bin/python -m pytest -q`.

## Контракт для Марка

Эти требования описывают клиент, не реализуют сервер. Зафиксировать их в общем OpenAPI перед объединением веток. На сервере сверять `Authorization: Bearer <service token>` в постоянное время. Токен отдельный от Telegram и Cloud.ru; `/internal` не публиковать через Caddy.

| POST маршрут | Поля запроса | Успех |
|---|---|---|
| `/internal/v1/telegram/link-request` | `bot_id`, `update_id`, `telegram_user_id`, `chat_id`, `code` | `link_request_id`, `status: pending` |
| `/internal/v1/telegram/updates` | те же четыре ID, `text`, `processing_mode: ai/manual` | `capture_id`, `job_id: UUID/null`, `status: saved`, `note_url` |
| `/internal/v1/telegram/voice` | multipart: те же четыре ID, `processing_mode: ai`, файл `audio` | тот же ответ сохранения |
| `/internal/v1/telegram/actions` | `bot_id`, `update_id`, `telegram_user_id`, `callback_token` | `status: completed/already_completed` |

ID Telegram — числа int64 (в multipart строковое представление), UUID — строки. Владелец определяется ядром по подтвержденной TelegramIdentity, а не по переданному `user_id`. Привязка по одноразовому коду должна требовать окончательного подтверждения в авторизованном вебе. Бот сам связь не подтверждает.

Ответ сохранения выдавать только после устойчивой записи исходника и транзакции задания. `note_url` — абсолютная защищенная ссылка на том же origin, что BERESTA_WEB_URL. Она должна открывать исходник/статус даже до завершения ИИ, например через capture_id; нельзя выдавать ссылку на еще не существующую Note. В ручном режиме job_id=null. Исходный текст сохраняется без trim; для `/save` удаляется только команда и один разделительный пробел.

Дедупликация на сервере: уникальный `(bot_id, update_id)` для всех входящих маршрутов. Повтор возвращает прежний результат; другой payload с тем же ключом — конфликт. Это необходимо при сбое между commit ядра и локальным checkpoint бота. Локальный offset не заменяет серверную дедупликацию.

Ошибка: `{"error":{"code":"telegram_not_linked","message":"..."},"operation_id":"..."}`. Текст `message` адаптер не пересылает: использует безопасный локальный словарь. Поддержанные отказы: `telegram_not_linked`, `link_expired`, `link_conflict`, `invalid_link`, `input_too_large`, `unsupported_audio`, `empty_input`, `action_forbidden`, `action_expired`, `quota_exceeded`. Это окончательный отказ операции; ядро не должно одновременно вернуть такой отказ и сохранить запись. При суточном лимите ИИ ручной режим остается доступен.

Неизвестный 401/403, отсутствующий маршрут 404/405 и нарушение схемы 422 останавливают процесс **без подтверждения update**. 5xx/сетевая ошибка/общий 429 удерживают offset и повторяют тот же ключ; для 429 поддерживается Retry-After. Не возвращать `telegram_not_linked` при неверном сервисном ключе.

## Поведение при сбоях

- Offset записывается атомарно с fsync после обработки каждого update, раньше следующего getUpdates. Поздние updates не перескакивают через неудачный.
- Один процесс на том состояния; файловая блокировка на macOS/Linux запрещает второй локальный poller. На разных серверах один токен одновременно не запускать.
- Нет скрытого повтора sendMessage после таймаута: запись уже сохранена, подтверждение доставки ответа неизвестно. Это отражается безопасным кодом в журнале. После падения между ответом и checkpoint возможен повтор ответа; отсутствие дубля записи обеспечивает ядро.
- Голос скачивается только с api.telegram.org по проверенному file_path. Проверяется реальный размер ≤10 МиБ и заявленная Telegram длительность ≤180 секунд. Формат и реальную длительность файла **обязано** проверять ядро до принятия; адаптер не является аудиодекодером.
- При длительной недоступности ядра Telegram не хранит updates бесконечно: документированный предел 24 часа. Отсутствие подтверждения «сохранено» означает, что пользователь не должен считать запись принятой. Нужен мониторинг остановленного процесса/возраста последнего успешного poll до production.
- Содержимое notes, коды привязки и URL с токеном не логируются. HTTPX/httpcore access logs отключены в entrypoint.

Поведение offset и срок хранения: [Telegram Bot API](https://core.telegram.org/bots/api#getupdates).

## Настройка после готовности ядра

1. Владелец создает тестового бота через официальный @BotFather. В чат передает только username, не токен.
2. Из корня запускает `.venv/bin/python -m telegram_adapter.setup_secrets`, вводит токен скрыто. Скрипт создает два файла с правами 0600 в игнорируемой Git папке secrets, существующие файлы не перезаписывает. Никаких сетевых запросов.
3. API ядра получает тот же **сервисный** токен из `secrets/telegram_service_token.txt`. Токен Telegram монтируется только адаптеру. Токен модели не передается адаптеру.
4. После появления маршрутов и настройки ядра можно запустить на macOS/Linux:

```sh
export BERESTA_BOT_NETWORK_ENABLED=true
export BERESTA_BOT_TOKEN_FILE="$PWD/secrets/telegram_token.txt"
export BERESTA_SERVICE_TOKEN_FILE="$PWD/secrets/telegram_service_token.txt"
export BERESTA_CORE_URL=http://127.0.0.1:8000
export BERESTA_WEB_URL=http://127.0.0.1:8000
.venv/bin/python -m telegram_adapter
```

Это реальный Telegram с тестовым аккаунтом; модель ядра оставить mock. Для публичного адреса требуется HTTPS. Без BERESTA_BOT_NETWORK_ENABLED=true процесс завершится до чтения секретов и сетевых обращений. Webhook должен отсутствовать; код не удаляет его автоматически.

## Контейнер после интеграции

`deploy/Dockerfile.telegram` и `deploy/compose.telegram.yaml` — отдельный образ и opt-in профиль. Общие Dockerfile, requirements и конфигурации Марка не менялись. Пример объединения конфигурации из корня: `docker compose -f compose.yaml -f deploy/compose.telegram.yaml --profile telegram config`. Перед запуском согласовать секрет ядра и сеть; текущий исходный API еще не поддерживает контракт.

В образе процесс имеет UID/GID 1000. На Linux файлы secrets должны читаться этим UID/GID, например root:1000 и 0440, каталог — root:1000 и 0750. Не делать файлы общедоступными. Для API настроить разрешение чтения сервисного токена отдельно, не монтировать туда токен Telegram.

Адаптер не публикует порты, имеет read-only root, постоянный том только для offset, ограничения ресурсов и отключенный автоматический restart на этапе интеграции. После полной проверки — включить контролируемый restart и мониторинг. Docker на текущем Mac не установлен; образ/Compose здесь не запускались.
