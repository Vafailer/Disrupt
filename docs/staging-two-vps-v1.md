# Staging на двух VPS

База этой ветки — integration/admin-ops-v1 d42b441. Контракты API, модели и миграции не меняются. Новая часть Марка для подключения не требуется.

## Конфигурация

Ядро запускается через `compose.staging.yaml` и `deploy/compose.core-private.yaml`. Используются mock-провайдеры, ключи моделей не монтируются. На ядре нужны секреты БД, внутреннего API и отдельный ключ псевдонимов статистики. Файлы находятся в `secrets`, не в Git. Их создание и права доступа проверяются оператором перед запуском. Секреты должны читаться пользователем приложения внутри контейнера, но не другими пользователями хоста.

На сервере бота используется отдельный `deploy/compose.bot-vps.yaml`. Нужны только токен Telegram и тот же сервисный токен. БД, аудио и ключи моделей туда не передаются. Сеть бота включается только явным `BERESTA_BOT_NETWORK_ENABLED=true`. Пока параметр выключен, бот завершается без чтения секретов. На этапе подготовки его не запускать с restart-политикой.

Между VPS оператор настраивает WireGuard. `CORE_VPN_IP` задаёт адрес интерфейса ядра, например `10.77.0.1`, но не публичный адрес, 0.0.0.0 или адрес общего LAN. На ядре API публикуется только на этом IP и порту 18000. Бот использует `http://CORE_VPN_IP:18000` внутри зашифрованного туннеля. Firewall должен разрешать этот порт только с VPN-адреса бота, включая правила Docker forwarding. Один bind на адрес не заменяет firewall. PostgreSQL не публикуется. Caddy на публичном домене закрывает `/internal/*`.

До запуска оператор проверяет с третьего хоста, что 18000 недоступен по публичному IP, и с VPS бота, что запрос к внутреннему API без токена получает 401. Доступ с токеном проверяется на mock-ядре синтетической записью. Не передавать токен аргументом curl или в логи. Реальные IP, DNS, firewall и WireGuard ещё не настроены и требуют серверов.

Команды выполняются из корня checkout после подготовки секретов и переменных.

```sh
docker compose --env-file .env.staging -f compose.staging.yaml -f deploy/compose.core-private.yaml up -d --build
# На VPS бота, после явного разрешения сети в его .env.bot
docker compose --env-file .env.bot -p beresta-bot -f deploy/compose.bot-vps.yaml up -d --build
```

Переменные ядра — APP_DOMAIN и CORE_VPN_IP. Переменные бота — CORE_VPN_IP, BERESTA_WEB_URL с HTTPS-доменом и BERESTA_BOT_NETWORK_ENABLED. Полный checkout одной опубликованной версии должен присутствовать на обоих хостах.

## Согласованное резервирование

Координатор работает на VPS ядра. Для управления удалённым Docker нужен заранее настроенный SSH alias `beresta-bot` с BatchMode, StrictHostKeyChecking=yes и проверенным known_hosts. Доступ к Docker равнозначен root; использовать отдельный ключ оператора, хранить вне Git. При недоступности узла команда должна завершаться, не ждать ввода пароля. Контекст создаётся один раз.

```sh
docker context create beresta-bot --docker host=ssh://beresta-bot
python3 deploy/ops/beresta_ops.py backup \
  --project beresta-staging --compose compose.staging.yaml \
  --compose deploy/compose.core-private.yaml --env-file .env.staging \
  --bot-context beresta-bot --bot-project beresta-bot \
  --destination /var/backups/beresta --recipient AGE_PUBLIC_RECIPIENT --maintenance
```

CLI требует SSH-контекст, один контейнер сервиса telegram и именованный том `/app/data`. Координатор сначала останавливает удалённого бота, затем локальных писателей. БД, аудио и состояние бота попадают в один архив с общим manifest и SHA-256. Чтение удалённого тома выполняется от UID 1000 в контейнере без сети, без секретов, с томом read-only; используется уже имеющийся образ бота. Если любой этап не выполнен, нового маркера успешной копии нет. Старый marker при неудаче остаётся старым; внешний монитор должен реагировать и на код возврата команды, а не только на возраст файла.

Ранее работавшие сервисы запускаются обратно, ранее выключенный бот не включается. Ошибка перезапуска удалённого бота даёт отдельный код ошибки и требует оператора; уже сохранённый архив при этом остаётся. При обрыве SSH после команды stop состояние бота может быть неизвестно. Проверить его на хосте и запустить вручную только после проверки отсутствия другого отправителя.

Все копии запускаются одним координатором из одного каталога с lock. Во время операции запрещены deploy, миграции, ручные перезапуски и второй координатор. SIGKILL или потеря сервера могут оставить процессы остановленными и временные открытые файлы; автоматическое восстановление после такого сбоя не заявляется. Нужны внешний мониторинг и инструкция оператора.

Monitor принимает те же `--bot-context` и `--bot-project` и отдельно сообщает недоступность или остановку удалённого контейнера. Это проверка процесса, а не heartbeat обработки Telegram. Копии нужно переносить во внешнее хранилище; расписание, уведомления и перенос пока не настроены.

Восстановление использует прежнюю изолированную команду restore. Оно проверяет БД и оригиналы, восстанавливает bot state и не запускает отправителей. Возврат в работу после аварии остаётся ручным из-за риска повторов при старом checkpoint.

## Проверки

Unit-тесты покрывают порядок остановки и запуска, отказ нешифрованного транспорта, ошибки операции и перезапуска, сохранение выключенного состояния. CI выполняет настоящий backup/restore с Docker SSH context на одноразовом runner. Два Compose-проекта используют один Docker daemon; это проверяет протокол координации и SSH, но не два физических VPS, задержки сети, firewall или WireGuard. Реальные Telegram и модели не вызываются. Приёмка на выбранных серверах остаётся обязательной до пользователей.
