# Сверка ядра и Telegram адаптера

Проверяем нашу ветку `feature/integration-v1-core` с адаптером коллеги
из `codex/telegram-adapter`, коммит `c63c3168aea59fb6d1c5dc50fd958346d43405c3`.
Его код используется без изменений. Ветки не объединены.

## Что исправлено в ядре

Бизнес-отказы получили коды, которые понимает адаптер. Непривязанный Telegram
возвращает telegram_not_linked. Истёкшая ссылка возвращает link_expired,
неизвестный код invalid_link, занятая связь link_conflict. Пустой текст и
превышение размера тоже дают окончательный отказ. Ошибки сервиса и формата
запроса остаются отдельными. При неверном сервисном секрете ответ 401.

Окончательный отказ сохраняется в Inbox без изменения пользовательских данных.
Повтор получает тот же ответ и operation_id. Временная ошибка откатывает Inbox,
исходник, задание и события. Заполненная очередь остаётся временным 429.
Суточная квота ещё не реализована.

Длины входящего кода и callback согласованы с адаптером. Выдаваемый код
остаётся случайным, 256 бит. Короткий ввод не становится действительным кодом.

POST /internal/v1/telegram/actions выполняет задачу по хешу токена Outbox.
Проверяются подтверждённая связь, владелец, бот, чат, задача, статус разрешённой
доставки и поколение напоминания. Выполнение, версии, история, событие и отмена
напоминаний записываются вместе. Конкурирующие вызовы выполняют задачу один раз.
Выдача кнопок и отправка напоминаний ещё не реализованы.

Для voice multipart разрешено тело до 10 МиБ + 64 КиБ служебных полей.
Другие запросы по-прежнему ограничены 128 КиБ. Считаются реально полученные
байты, заголовок Content-Length не заменяет проверку.

## Что передать коллеге

Общий контракт есть в `docs/integration-v1.yaml` и
`docs/integration-v1.openapi.json`. Это одна автоматически созданная схема.
Запросы и ответы собраны в `docs/integration-v1-examples.json`.
Для обновления из корня выполнить `PYTHONPATH=. python scripts/export_contract.py`.
Методы без реализации помечены contract-only.

В адаптере нужно отдельно обработать `409 conflict`. Сейчас он повторяет
неизменяемый конфликт update ID бесконечно. Следует остановить процесс без
подтверждения update и передать ошибку оператору. Известные бизнес-коды 409
при этом остаются обычными отказами пользователю. Клиентский файл не меняли.

`app/audio_storage.py` и `app/routes/audio.py` пишет основатель.
Наш middleware готов принять multipart, но самого voice маршрута пока нет.
Основатель должен проверить файл до 10 МиБ, его фактический формат и
длительность до 180 секунд, устойчиво сохранить исходник и обработать повтор.
Подключение маршрута и STT остаются на нашей стороне после передачи модуля.
Сейчас отправка голоса получает 404 и останавливает адаптер.

Для note_url задать одинаковый origin в NOTES_PUBLIC_ORIGIN и BERESTA_WEB_URL.
NOTES_INTERNAL_API_TOKEN_FILE ядра и BERESTA_SERVICE_TOKEN_FILE адаптера должны
содержать один сервисный секрет. Telegram токен в ядро не передаётся.

В обеих ветках изменён только один общий файл, AGENTS.md. При объединении
сохранить правила совместной работы коллеги и наши правила оформления текста.
Изменения CI в нашей ветке добавляют проверку клиента по фиксированному SHA.
Это временная проверка совместимости, после объединения можно использовать
адаптер из общего checkout. Название нашей ветки не менять.

## Как повторить проверку

Из корня, оставаясь в своей ветке, получить клиент в отдельный временный каталог.
Не использовать checkout или merge для этого.

```sh
git fetch origin
mkdir -p /tmp/beresta-telegram-adapter
git archive c63c3168aea59fb6d1c5dc50fd958346d43405c3 telegram_adapter | tar -x -C /tmp/beresta-telegram-adapter
TEST_TELEGRAM_ADAPTER_PATH=/tmp/beresta-telegram-adapter python -m pytest -q
python -m ruff check app tests migrations scripts
```

Тесты используют настоящие CoreClient и Bot коллеги с нашим FastAPI через
ASGITransport. Ответы Telegram подменены. Проверяются AI и ручной текст,
сохранность пробелов, повторы, pending привязка, бизнес-отказы, ошибки сервиса
и выполнение задачи через callback. Для callback создаётся тестовая Outbox,
это не проверка выдачи кнопок или реальной доставки.

Отдельно проверяются конкурентные действия, отменённая кнопка, чужой аккаунт,
неотправленная доставка и откат транзакции. Тест middleware проверяет поток
байтов, а не корректность аудиофайла. В CI есть отдельная PostgreSQL.

Живой Telegram, STT, контейнер и production здесь не проверяются.
Ключ Cloud.ru не читается и не используется. Успех этих тестов не означает
готовность всего MVP.

Локальная проверка 5 октября 2026 года прошла с 126 passed и 2 skipped.
Пропущены PostgreSQL-тесты, локального сервера БД нет. Линтер и проверка
синтаксиса основного веба прошли. Повторная генерация контрактов даёт те же
файлы. PostgreSQL 17, миграции и конкурентный callback проверяет CI этой ветки.
