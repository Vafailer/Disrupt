# Развёртывание на выбранных VPS

Фактические службы, проверки и оставшиеся действия записаны в [server-deploy-result-v1.md](server-deploy-result-v1.md).

База ветки `feature/server-deploy-v1` соответствует `5632fb3`, PR #13. `main` и незавершённые локальные изменения не менялись.

## Режим подготовки

Ядро использует отдельный проект `beresta-pilot` и production Compose с overlays `core-private`, `limits` и, до домена, `pre-domain`. Адрес API равен `10.77.0.1:18000`. PostgreSQL наружу не публикуется. Публичный Caddy до регистрации домена отвечает 503, а `/internal` и `/internal/*` возвращают 404.

API сохраняет задания режима `cloudru`, но сам не получает ключ. `NOTES_AUTO_WORKER=false`, `NOTES_ALLOW_LIVE_REQUESTS=false`. Worker имеет профиль `owner-live` и `restart=no`. Даже явно запущенный worker откажется читать ключ при выключенном разрешении. Обычный `up -d` его не включает. Расписание напоминаний работает отдельным scheduler без доступа к модели.

Бот получает только свой Telegram-токен и общий сервисный токен. Контейнер создаётся один, с отдельным томом состояния. До домена и ввода токена он остаётся остановленным. Подготовительный overlay выключает сеть и автоперезапуск. Проверки не создают пользовательские задания в базе пилота.

Логи ядра ограничены тремя файлами по 5 МиБ на контейнер. На боте сохраняются два файла по 5 МиБ. Ограничения памяти заданы отдельным overlay. Не использовать `system prune --volumes`, `volume prune` и `down -v` на пилоте или боте. Допустимое удаление касается только явно выбранного изолированного проекта восстановления.

Docker daemon также ограничивает логи новых контейнеров. Кэш сборки имеет целевой предел 512 МиБ на боте и 2 ГБ на ядре. Очистка касается восстанавливаемого кэша, тома не затрагиваются. Journald ограничен 100 МиБ на диске и 50 МиБ в памяти.

## Firewall

`deploy/host/beresta-firewall` рассчитан на Docker с iptables backend. Он добавляет свои цепочки без очистки существующих правил. `DOCKER-USER` проверяет исходный порт до DNAT. Порт 18000 разрешён только с `10.77.0.2` через интерфейс `beresta` к `10.77.0.1`. INPUT дополнительно закрывает этот порт для host-процесса и userland proxy. IPv6-доступ закрыт. SSH и WireGuard не меняются.

Служба `beresta-firewall` применяет правила при загрузке. Docker drop-in повторяет применение после каждого старта daemon. Установка не требует немедленного перезапуска Docker. До приёмки нужно проверить запрет с публичного адреса, разрешение из контейнера бота и сохранение правил после перезапуска Docker. Существующие ключи WireGuard остаются прежними.

Запрет в FORWARD применяется только к исходному направлению conntrack. Ответные пакеты должны проходить через штатные правила Docker. Иначе правило по исходному порту блокирует SYN-ACK и туннельный клиент получает тайм-аут.

На ядре Docker ждёт запуск WireGuard. При загрузке приватный адрес должен появиться до восстановления контейнера API и его публикации порта.

Правила основаны на [документации Docker](https://docs.docker.com/engine/network/packet-filtering-firewalls/). Настройка файла сама по себе не подтверждает фильтрацию на VPS.

## Секреты и копии

Секреты хранятся вне Git в каталоге `secrets` с правами 0700. Файлы для приложений имеют владельца UID 1000 и права 0400. Значения не выводятся. `save-secret.py` запрашивает секрет скрытым вводом в интерактивном SSH, не делает сетевых обращений и не запускает службы. Он может заполнить пустой подготовительный файл, но не перезаписывает существующий секрет.

Ключ age создаётся на ПК и хранится отдельно от VPS. На ядре нужен только публичный получатель в `/etc/beresta/backup-recipient`. Ключи БД, статистики и конфигурацию следует хранить в отдельной защищённой копии на ПК. Архив данных приложения их не включает.

Координатор использует отдельный серверный SSH-ключ для Docker context `beresta-bot`. Приватный SSH-ключ ПК на серверы не передаётся. На боте следует ограничить этот новый ключ адресом `10.77.0.1` и forced command `/usr/bin/docker system dial-stdio`, отключить forwarding и PTY. Доступ к Docker равнозначен root. Host key брать из проверенного SSH-сеанса, не доверять непроверенному `ssh-keyscan`.

`beresta-backup` сохраняет БД, аудио и состояние удалённого бота в один зашифрованный архив. Ранее выключенные службы остаются выключенными. Таймер устанавливается, но включается только после успешной пробной копии. Его время равно 04:00 Москвы с задержкой до двух минут. Старые архивы автоматически не удаляются. Перенос на ПК и контроль диска необходимы после каждой копии.

Restore допускает `--identity -`. Владелец может передать ключ через stdin защищённого SSH-сеанса. Ключ проходит через память процесса age, но не сохраняется на диске VPS. Восстановление создаёт новый проект `beresta-restore-*` без отправителей Telegram, приложения и публичных портов. После успеха проверенные тестовые тома можно удалить только у этого проекта.

## Домен и первое пользовательское испытание

9 октября настроен `https://app.berestaapp.ru`, сертификат и публичные ограничения проверены с Хельсинки. Настройки адреса ядра и бота обновлены. Регистрация, worker и сеть бота пока выключены. Первые два шага ниже описывают общую настройку; для текущего поддомена DNS и HTTPS уже выполнены. Для создания аккаунтов регистрацию нужно открыть только на согласованное время.

1. Зарегистрировать домен самостоятельно. Для выбранного имени веба создать A-запись со значением `178.217.98.101`. Например, для `app.example.ru` имя записи равно `app`. AAAA пока не создавать. Для бота DNS не требуется.
2. На ядре изменить `APP_DOMAIN` в `.env.production` на выбранное имя. Оставить разрешение Cloud.ru выключенным. Временно включить регистрацию. Создать `/etc/beresta/domain-ready` и выполнить `beresta-core up -d db api scheduler caddy`. Проверить действительный HTTPS-сертификат и 404 для обоих публичных внутренних путей.
3. Создать два аккаунта. Затем выключить регистрацию и пересоздать API через `beresta-core up -d api`. Проверить вход обоих владельцев и запрет доступа к чужой заметке.
4. Ключ Cloud.ru уже сохранён владельцем на ядре через скрытый SSH-ввод. Пока worker выключен, запросов к модели не будет.
5. Telegram-токен уже сохранён на боте, `getMe` подтвердил его имя. В `.env.bot` подготовлен `https://berestaapp.ru`. После проверки HTTPS, связи и согласованной копии установить `BERESTA_BOT_NETWORK_ENABLED=true`. Убедиться, что других экземпляров нет. Запустить `beresta-bot up -d --scale telegram=1 telegram` без подготовительного overlay.
6. Владелец устанавливает `NOTES_ALLOW_LIVE_REQUESTS=true` в `.env.production`. На первый текст лимиты остаются равны 1. Выполнить `beresta-core --profile owner-live up -d worker`. Отправить одну короткую текстовую запись и дождаться результата. Повторно не отправлять запись с неопределённым исходом. Проверить исходник, заметку и расход слота. Затем остановить worker через `beresta-core stop worker`.
7. Для следующего обращения увеличить общий и пользовательский лимиты с учётом уже занятых слотов. Проверить привязку Telegram к веб-аккаунту и доставку одного напоминания. Сделать новую копию, скачать её на ПК и сравнить SHA-256.

Автоматическое распознавание аудио не входит в первый тест. Оригинал можно принять и скачать. Без STT после включения worker задание получит `stt_not_configured`, файл сохранится.

После HTTPS безопасная проверка из одноразового контейнера образа бота принимает `deploy/ops/probe_core.py --public-origin https://app.berestaapp.ru`. Она проверяет сертификат, веб и health, отказ админки без сессии, внутреннюю авторизацию и публичный запрет API. Telegram и модель не вызываются, записи не создаются. Без `--public-origin` остаётся проверка старой заглушки с 503.

Для окна регистрации установлен `/usr/local/sbin/beresta-registration.py` из `deploy/host/registration-window.py`. Команды `open` и `close` меняют только регистрацию и пересоздают только API без зависимостей и сборки. Перед открытием оператор задаёт таймер закрытия с абсолютным `OnCalendar` в UTC и `Persistent=true`. Установленные службы называются `beresta-close-registration.timer` и `beresta-close-registration.service`. После создания аккаунтов закрыть раньше через `beresta-registration.py close`; существующие аккаунты и сессии сохраняются.

## STT

В ветке добавлен кандидат `CloudRuSpeechProvider` для multipart POST `/audio/transcriptions`. Он ограничивает вход и ответ, не повторяет запросы и не следует redirect. STT и LLM занимают отдельные долговечные слоты. Транскрипт сохраняется до LLM. Тесты используют только вымышленные ключи и `httpx.MockTransport`.

[Каталог Cloud.ru](https://cloud.ru/docs/foundation-models/ug/topics/overview__available__models) перечисляет Whisper. [Публичная спецификация Cloud.ru](https://cloud.ru/docs/foundation-models/ug/topics/api-ref__specs) описывает только models и chat completions. Multipart-формат кандидата взят из [OpenAI Audio API](https://developers.openai.com/api/reference/resources/audio/subresources/transcriptions/methods/create). Совместимость программного шлюза с этим методом является предположением и не проверена.

STT остаётся выключенным. Для включения владелец должен получить подтверждённый протокол и модель шлюза, затем явно задать `NOTES_STT_ENABLED=true`, `NOTES_STT_PROTOCOL_CONFIRMED=true` и `NOTES_STT_MODEL`. Worker Compose передаёт эти настройки, по умолчанию они выключены. Проверка шлюза и включение описаны в [voice-text-replies-v1.md](voice-text-replies-v1.md), разовая проверка `python -m app.stt_readiness`. Не включать их на основании одного названия модели в каталоге.
