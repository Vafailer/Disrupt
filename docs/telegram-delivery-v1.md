# Отправка напоминаний

Ветка `feature/reminder-delivery-v1` продолжает работу коллеги по боту. Она создана от `feature/audio-web-v1`, коммит `2e8acc6296bf5ba2bf7d3ee5705d84b9c01e6ef1`. Здесь уже есть его Telegram и аудиомодули, подключённые к ядру. Ветки коллеги и main не объединялись.

## Что добавлено

`app/scheduler.py` работает отдельным процессом рядом с PostgreSQL. Каждые пять секунд выбирает подтверждённые напоминания с наступившим сроком. Под блокировкой аккаунта ещё раз проверяет владельца, открытую задачу, поколение и доступную Telegram-связь. Создаёт одну Outbox на пару reminder_id и generation. Перезапуск и два scheduler не создают дубль. Уже поставленные в очередь записи не занимают лимит следующего прохода.

При нескольких ботах выбирается самая ранняя доступная связь по created_at и id. Для MVP предполагается один рабочий бот. При переносе на новый бот сначала отключите уведомления старой связи. Уже созданная Outbox сохраняет своего получателя, смена связи не перенаправляет её автоматически.

`telegram_adapter/delivery.py` работает отдельной асинхронной задачей в том же процессе бота. Long polling не задерживает напоминания. Задача получает один claim, проверяет ответ и вызывает authorize непосредственно перед отправкой. Только send=true разрешает один sendMessage. Для задачи есть кнопка «Выполнено», для заметки только ссылка на запись. Текст отправляется без Markdown и HTML.

Получение authorize ограничено десятью секундами. Сама отправка тоже ограничена десятью секундами целиком, включая ожидание соединения и чтение ответа. Минимальный lease ядра равен тридцати секундам. Потерянный ответ authorize не даёт разрешения на отправку.

## Сбои и повторы

| Результат Telegram | Что сохраняется |
|---|---|
| Успех с message_id и ожидаемым chat_id | sent |
| Подтверждённый 403 | blocked, ядро отключает доставку этой связи |
| Подтверждённый 429 с целым retry_after от 0 до 86400 | retryable, новая попытка после задержки |
| Timeout, 5xx, плохой JSON или противоречивый ответ | unknown, без повторной отправки |
| Подтверждённый 401 | unknown и остановка процесса после записи результата |

Код 400 тоже оставляет unknown. Текущий контракт не имеет отдельного статуса окончательной ошибки отправки. Адаптер не добавляет свой статус и не выдаёт такой отказ за безопасный повтор.

Задержка 429 действует в ядре для этой доставки и в работающем sender для следующих отправок. При перезапуске локальная задержка общей очереди сбрасывается, но серверный retry_at этой доставки сохраняется. Ошибки и таймауты не печатают ответ Telegram, URL, токены или текст.

После ответа Telegram бот сохраняет результат в файл рядом с offset, с суффиксом `.delivery.json`. Запись атомарная, с fsync файла и каталога, права 0600. Там только bot_id, delivery_id и тело result. Текст, chat_id и callback не сохраняются. Lease_token нужен для повтора result, поэтому файл считается секретом. Том состояния должен оставаться закрытым, доступным только процессу бота и администратору.

До подтверждённого result новый claim не берётся. Потерянный ответ ядра и перезапуск приводят к повтору того же result. Повторного sendMessage нет. Повреждённый файл, другой bot_id или открытые права останавливают процесс, файл не удаляется по догадке. Файл удаляется только после status=recorded. При падении между sendMessage и сохранением файла попытка истечёт в ядре как unknown.

Фатальная ошибка одной задачи останавливает обе. Входящий offset и журнал доставки независимы. Для одного токена остаётся один процесс бота и один том состояния.

## Подключение

Модели, миграции, API, main.py и зависимости не менялись. Scheduler добавлен в локальный и production Compose. Production scheduler получает только пароль БД, работает с mock-настройкой и не получает ключ модели или токен Telegram.

Overlay `deploy/compose.telegram.yaml` передаёт один сервисный секрет API и боту. Токен Telegram остаётся только в боте. Для локальной конфигурации задайте BERESTA_WEB_URL тем же origin, что NOTES_PUBLIC_ORIGIN API. Для production задайте BERESTA_WEB_URL равным HTTPS-адресу APP_DOMAIN. Для разнесённых серверов нужна отдельная закрытая сеть между ботом и API, текущий overlay описывает запуск на одном сервере.

Проверить конфигурацию без запуска и чтения значений секретов можно так.

```sh
docker compose -f compose.yaml -f deploy/compose.telegram.yaml --profile telegram config --quiet
APP_DOMAIN=example.invalid docker compose -f compose.production.yaml -f deploy/compose.telegram.yaml --profile telegram config --quiet
```

Бот по-прежнему выключен без BERESTA_BOT_NETWORK_ENABLED=true. Агент его в сеть не запускал. Команды настройки секретов и права UID описаны в [инструкции адаптера](telegram-adapter.md). Production ещё требует настройки сети, мониторинга и проверки восстановления.

Scheduler можно запустить отдельно после миграций, с тем же NOTES_DATABASE_URL, что у API.

```sh
python -m app.scheduler
python -m app.scheduler --once
```

## Проверки

```sh
python -m pytest -q
python -m ruff check app tests migrations scripts telegram_adapter
```

Тесты используют текущий FastAPI, CoreClient и Bot с подменённым Telegram. Проверяются конкурентные scheduler, чужие владельцы, закрытая задача, отключённая связь, новая generation, отмена между claim и authorize, потерянный authorize, unknown, 403, 429, 401, потерянный ответ result, перезапуск и кнопка выполнения. Отдельный сценарий доставляет тридцать вымышленных напоминаний ровно по одному разу. В PostgreSQL проверяется конкуренция scheduler и отмены.

CI также проверяет Compose, собирает оба образа и запускает офлайн-демо бота. Проверка тридцати сообщений на mock не подтверждает срок +60 секунд в настоящем Telegram. HTTPS staging, реальная доставка, админка, backup и восстановление ещё не завершены. Ключ Cloud.ru не используется.

Локально 6 октября прошли 337 тестов. Семь проверок PostgreSQL пропущены, локального сервера БД нет. Ruff, обе проверки DOM веба, офлайн-демо и воспроизводимость OpenAPI прошли. Статус CI с PostgreSQL и образами нужно смотреть для опубликованного SHA, результат будет записан в PR.

Формат sendMessage и поле retry_after сверены с [официальным Telegram Bot API](https://core.telegram.org/bots/api#sendmessage). Контракт ядра описан в [reminder-core-v1.md](reminder-core-v1.md).
