# Резервные копии и восстановление

Ветка `codex/operations-v1` основана на `codex/admin-ui-v1` (`aa4a933`). Модели, миграции, API и код Марка не меняются. Единственная правка общего runtime-файла находится в `deploy/Caddyfile`. Публичные `/internal` и `/internal/*` возвращают 404. Бот обращается к API напрямую во внутренней сети.

## Резервная копия

На сервере нужны Docker Compose v2, Python 3.11+ и age. Команды выполняет оператор с доступом к Docker. Этот доступ равнозначен root. Сначала проверить на staging с mock-провайдерами. Скрипт не загружает настройки приложения или ключ модели.

Создать ключ age на отдельном доверенном компьютере через `age-keygen -o recovery.key`. Закрытый ключ хранить вне сервера и репозитория. На сервер передать только публичного получателя из `age-keygen -y recovery.key`. Потеря закрытого ключа делает восстановление невозможным.

Пример для локального mock-стенда, из корня репозитория.

```sh
python3 deploy/ops/beresta_ops.py backup \
  --project beresta-staging --compose compose.yaml \
  --destination /var/backups/beresta --recipient AGE_PUBLIC_RECIPIENT \
  --maintenance
```

`--project`, Compose-файлы и `--env-file` должны совпадать с реально запущенным окружением. Для бота добавить `--compose deploy/compose.telegram.yaml --telegram`. Пропуск `--telegram` при найденном контейнере бота запрещён. Для production указывать production Compose вместо локального; не запускать пример локального стенда на production.

Копируется PostgreSQL, оригиналы аудио и, при включённом боте, offset и журнал доставки. Скрипт на короткое время останавливает работающие API, worker, scheduler и бот. В это время веб недоступен, напоминания задерживаются. После чтения данных запускаются только ранее работавшие сервисы. Миграции и любые другие процессы записи на время копирования должны быть остановлены оператором. Не запускать второй экземпляр приложения на тех же томах.

Архив содержит контрольные суммы и шифруется age. Каталог имеет права 0700, файлы 0600. Временные открытые данные удаляются при штатном завершении или исключении. Авария питания или SIGKILL может оставить `.working-*`; после проверки отсутствия работающего backup удалить такой каталог вручную. Диск сервера должен быть зашифрован. Свободного места нужно минимум на открытый набор данных, внешний tar и зашифрованный архив; планировать запас не менее трёх размеров копии.

`latest.json` появляется только после сохранения зашифрованного архива. Автоматического удаления старых копий нет. После каждой копии переносить `.tar.age` на отдельный хост или хранилище и сверять SHA-256 из результата команды. Хранить минимум 7 ежедневных копий. Внешнее хранилище и расписание пока не настроены; копия только на том же сервере не защищает от потери сервера.

## Проверка восстановления

```sh
python3 deploy/ops/beresta_ops.py restore \
  --project beresta-restore-check01 \
  --bundle /secure/beresta-DATE.tar.age \
  --identity /secure/recovery.key --work-dir /secure/recovery-work
```

Разрешён только новый проект `beresta-restore-*`. Существующие тома не перезаписываются. Используется отдельный Compose без внешних портов, приложения, worker, scheduler, бота и ключей моделей. PostgreSQL доступен только в изолированной сети восстановления. Внутри неё используется trust; сторонние контейнеры в эту сеть не подключать.

Проверяются структура архива, SHA-256 файлов, успешный `pg_restore` и байты каждого оригинала в восстановленном томе относительно метаданных БД. При ошибке база останавливается, тома сохраняются для разбирательства. При успехе остаётся только БД; вывод не содержит записей пользователей. После проверки удалить именно этот тестовый проект через `docker compose -p beresta-restore-check01 -f deploy/ops/restore.compose.yaml down -v`.

Это проверка восстановления, а не автоматическое переключение production. При реальной аварии оператор должен остановить старых отправителей, выбрать подтверждённую копию, проверить данные и журнал Telegram, затем отдельно подключить приложение. Восстановление устаревшего offset или журнала может повторить ранее обработанные события. Автоматический запуск бота после восстановления запрещён.

## Контроль состояния

```sh
python3 deploy/ops/beresta_ops.py monitor \
  --project beresta-staging --compose compose.yaml \
  --backup-dir /var/backups/beresta
```

Для бота добавить тот же overlay и `--telegram`. Команда читает состояния контейнеров, `/health`, счётчики зависших заданий и доставок, свободное место в каталоге копий и возраст последней копии. При проблеме возвращает код 1 и JSON с кодами сигналов. Не выводит тексты заметок, chat ID или токены. Статус unknown требует проверки оператором, а не повторной отправки.

Проверку следует запускать каждую минуту внешним мониторингом с оповещением оператору; backup ежедневно в согласованное окно. Эти интеграции ещё нужно настроить на выбранном сервере. Проверка не заменяет внешний HTTPS-probe, контроль диска Docker, heartbeat зависшего процесса, доступность Telegram и тест реального напоминания. Целевое восстановление по времени и допустимую потерю данных можно подтвердить только на выбранном сервере.

## Проверки разработки

`tests/test_operations.py` проверяет защиту архивов, отказ перезаписи и перезапуск сервисов при ошибке. `operations.yml` поднимает PostgreSQL 17 и mock-приложение, сохраняет синтетическую запись и оригинал, шифрует копию, восстанавливает отдельное окружение и проверяет блокировку внутренних HTTP-маршрутов. Реальные Telegram, STT и production эта проверка не вызывает.
