# Шифрование данных на диске

Тексты заметок и голосовые записи лежат на сервере в зашифрованном виде. Дамп базы или папка с аудио сами по себе ничего не раскрывают. Шифрование идёт на стороне приложения, AES-256-GCM, один ключ сервера из файла. Ключ не хранится ни в базе, ни в Git, ни в резервных копиях.

## Что шифруется

В базе:

- `captures.original_text`, `captures.transcript`, `transcript_revisions.text`
- `notes.title`, `notes.markdown`, `notes.conclusions`, `revisions.snapshot`
- `items.text`, `items.source_quote`, `items.due_text`
- `reminders.text`
- `outbox.message_text` (разовые сообщения, например ссылка для сброса пароля)
- `inbox.response` (ответы на запросы бота, в них бывает текст заметки)
- `assistant_requests.question`, `assistant_requests.result`
- `feedback.subject`, `feedback.description`, `feedback.steps`, `feedback.expected`, `feedback.contact`
- `admin_accounts.totp_secret`

В папке аудио шифруются сами файлы оригиналов. Размер и SHA-256 в базе остаются про исходное аудио.

## Что не шифруется

Идентификаторы, время, статусы, версии, имена пользователей, почта, названия категорий (на них стоит уникальный индекс), хеши (пароли, токены, `request_hash`, `payload_hash`, `audio_sha256`), метрики и события продукта, имена файлов аудио. По хешу нельзя прочитать текст, но можно проверить догадку о нём.

Шифрование не защищает от того, кто уже получил доступ к работающему серверу вместе с ключом. Во время обработки текст уходит модели в открытом виде, это часть продукта. Дамп `pg_dump` без ключа бесполезен, но не стоит считать его публичным.

## Как это устроено

- Значение в базе выглядит как `enc:v1:<key_id>:<base64url(nonce + шифртекст)>`. Nonce из 12 случайных байт новый для каждой записи.
- В AAD входит метка столбца вроде `notes.markdown`. Значение, скопированное в другой столбец, не расшифруется.
- `key_id` это первые 8 символов SHA-256 от ключа. По нему приложение находит нужный ключ при ротации.
- Значения без префикса `enc:` считаются старым открытым текстом и читаются как есть. Так переход не ломает существующие заметки.
- Аудиофайл начинается со строки `BERESTA-ENC1`, дальше идут `key_id`, nonce и шифртекст. В AAD входит имя файла. Старые файлы без заголовка проигрываются как раньше.
- Поиск по заметкам идёт в Python после расшифровки, потому что SQL не видит текст. Для личной библиотеки это быстро. Результаты и порядок те же.
- Админские метрики и выгрузка столбцы с содержимым не читают.

## Настройки

| Переменная | Значение |
| --- | --- |
| `NOTES_DATA_ENCRYPTION` | `required` или `off`. По умолчанию `off` (только для разработки). |
| `NOTES_DATA_KEY_FILE` | Файл с ключом, 32 случайных байта в base64. |
| `NOTES_DATA_OLD_KEY_FILES` | Старые ключи через запятую. Нужны только при смене ключа. |

С `required` и без читаемого верного ключа приложение, worker, scheduler и админская команда не запустятся. С `off` новые данные пишутся открытыми. Читать зашифрованное можно в обоих режимах, если ключ задан. Без ключа чтение зашифрованного значения даёт понятную ошибку про `NOTES_DATA_KEY_FILE`.

В `compose.production.yaml` и `compose.staging.yaml` режим `required` уже включён. Ключ монтируется как Docker secret `data_key` из `secrets/data_key.txt` в api, worker и scheduler.

## Ключ

Создайте ключ один раз и не перезаписывайте существующий файл.

```sh
umask 077
openssl rand -base64 32 > secrets/data_key.txt
```

То же даёт `python -m app.data_crypto generate-key`. Команда печатает только ключ.

Храните ключ отдельно от резервных копий базы и аудио. Нужна ещё одна копия вне сервера, например в менеджере паролей владельца или на офлайн-носителе. Если ключ потерян, тексты и записи не восстановить, резервные копии тоже. Не отправляйте ключ в чат, issue или Git.

## Включение на сервере

1. Сделайте свежую резервную копию по [operations-v1.md](operations-v1.md). Проверьте, что она открывается.
2. Создайте `secrets/data_key.txt` и сохраните копию вне сервера.
3. Соберите образ заново. В `requirements.txt` добавлена библиотека `cryptography` с `cffi` и `pycparser`, поэтому образ из `deploy/Dockerfile.runtime-reuse` не подойдёт. Нужна полная сборка по обычному `Dockerfile`.
4. Запустите миграции. Миграция `c9e4a1b2d3f6` только расширяет короткие текстовые столбцы до `TEXT`, данные она не меняет.
5. Пересоздайте сервисы с ключом.

```sh
docker compose --env-file .env.production -f compose.production.yaml up -d --force-recreate api worker scheduler
```

6. Зашифруйте то, что уже лежит в базе и в папке аудио.

```sh
docker compose --env-file .env.production -f compose.production.yaml exec api python -m app.data_crypto encrypt-existing
```

Команда идёт пачками, ничего не печатает кроме чисел и безопасна при повторном запуске. Значения с текущим ключом она пропускает. Строки блокируются на время пачки, поэтому правки пользователей не теряются. Лучше запускать в тихое время.

7. Проверьте результат.

```sh
docker compose --env-file .env.production -f compose.production.yaml exec api python -m app.data_crypto status
```

Для каждого столбца и для `audio` видны числа `plain`, `current`, `old`. После шага 6 нужно `plain=0` и `old=0`.

8. Сделайте новую резервную копию. Старые копии до шифрования содержат открытые тексты. Когда новая проверена, старые удалите.

## Смена ключа

1. Создайте новый ключ, например в `secrets/data_key_new.txt`.
2. Старый ключ положите в `secrets/data_key_old_1.txt`.
3. В compose добавьте старый ключ как secret для api, worker и scheduler. Новый файл станет `data_key`.
4. В `.env.production` задайте `NOTES_DATA_OLD_KEY_FILES=/run/secrets/data_key_old_1`.
5. Пересоздайте сервисы и выполните `encrypt-existing`. Значения со старым ключом будут перешифрованы новым (в отчёте это `rotated`).
6. Убедитесь по `status`, что `old=0`. Только после этого уберите старый ключ из настроек. Хранить его в архиве ещё какое-то время разумно, пока живы старые резервные копии.

## Откат

Поставьте `NOTES_DATA_ENCRYPTION=off` и оставьте `NOTES_DATA_KEY_FILE`. Приложение продолжит читать зашифрованное и будет писать новое открытым. Массовой расшифровки в CLI нет, она не нужна для работы.

## Для разработчиков

- Новый столбец с содержимым пользователя объявляйте типом `EncryptedText("таблица.столбец")` или `EncryptedJSON("таблица.столбец")` из `app/encrypted_types.py`. Тест `tests/test_encryption.py` сверяет список столбцов и метки.
- Такие столбцы нельзя использовать в `WHERE`, `ORDER BY`, `LIKE` и функциях SQL. Фильтруйте в Python.
- Тесты идут с включённым шифрованием, ключ создаётся в `tmp_path` (см. `tests/conftest.py`).
- Живой сервис в проверках не нужен и не используется.

## Что проверено

Шифрование и расшифровка, подмена данных, неверный ключ, чужой столбец, старые значения, смена ключа, поиск, аудио на диске и CLI покрыты тестами в `tests/test_encryption.py`. Они идут в CI. Работа на PostgreSQL с настоящим ключом и на сервере не проверена. Владелец проверяет её при включении по списку выше.

На время загрузки аудио открытая копия лежит во временном файле `.upload-*` в папке аудио и удаляется сразу после сохранения. После аварийной остановки процесса такой файл может остаться. Его можно удалить вручную.
