# Четыре дня до пилота Beresta

План рассчитан на 6-9 октября 2026 года. Вечер 5 октября ушёл на разбор проекта
и первый этап ядра. Если считать 5 октября первым полным днём, сроки сдвигаются
на сутки раньше. Проверки перед запуском остаются теми же.

## Что есть в проекте

На начало работы main был на коммите `90b4dd5`. Уже работали регистрация,
сессии, CSRF, Capture, Job, Note, Revision и очередь обработки с сохранением
в БД. Были mock, адаптер модели, простой веб и конфигурации PostgreSQL и HTTPS.
Счётчик провайдера учитывал зарезервированные вызовы, а не расходы в рублях.
Telegram, STT, задачи, категории, напоминания, поиск и продуктовая аналитика
отсутствовали. Развёртывание рабочего сервера ещё не подтверждено.

Оставляем FastAPI, PostgreSQL и статический веб. API, AI worker и scheduler
запускаются отдельно, используют общее ядро и БД. Telegram-адаптер работает
за рубежом и обращается только к внутреннему API российского ядра.
Аудиохранилище и резервное копирование делает основатель. Их работу нужно
проверить на сервере, наличия конфигурации для этого недостаточно.

Новое ТЗ включает админку в MVP и меняет распределение работы. PWA, offline,
граф, семантический поиск и персонализацию оставляем на потом.
Агент не использует ключ Cloud.ru, в том числе для `/models` и проверки баланса.
Разработка идёт на mock, без перехода к живой модели при ошибке. Качество
ответов настоящей модели проверяет владелец ключа.

## Что сделано в этой ветке

- Добавлены общие модели и новая миграция.
- Telegram привязывается по одноразовому коду с подтверждением в вебе.
  В БД хранится хеш кода. Срок действия ограничен. Аккаунты не сливаются.
- Внутренний API принимает текст с сервисной авторизацией. Ответ saved
  возвращается после записи в БД. Inbox обрабатывает повторы, в том числе
  одновременные. Повтор с изменёнными данными отклоняется.
- Веб и Telegram могут сохранить текст без ИИ. Ссылка на Capture доступна
  до появления готовой заметки.
- Добавлены серверные роли, защита страницы и файлов админки, команда выдачи роли.
- Сервер записывает первые события без содержимого заметок. Одна аналитическая
  сессия может включать действия в вебе и Telegram.
- Для второго разработчика подготовлены контракт API и пример JSON админки.
  Методы, которые ещё предстоит написать, отмечены в схеме.

Первый день пока не принят. Остались проверка настоящего бота на staging,
ревью авторизации и миграций вторым разработчиком, тесты PostgreSQL в CI.

## Что может задержать работу

1. Владелец ещё не подтвердил STT endpoint, модель, формат аудио, тариф
   и дневные лимиты. Пока используем mock. Неизвестный расход не считаем нулём.
2. Scheduler зависит от контракта доставки. Отправка прямо из confirmed
   не учитывает отмену и случай, когда результат сетевого запроса неизвестен.
3. Время напоминания и зону IANA должен подтвердить пользователь. Молча угадывать нельзя.
4. Старые аккаунты и тестовые данные не должны искажать когорты.
5. Ещё предстоит проверить HTTPS, закрытый внутренний API, резервное копирование,
   восстановление и работу с пилотными пользователями.

## Что коллега может брать сейчас

Модели и integration-v1 доступны в этой ветке. Для бота уже работают
link-request и updates. Админку можно делать по примеру JSON и схеме.
API summary/export пока нет. Scheduler можно подготовить по Reminder/Outbox,
а доставку подключить после реализации claim/authorize/result.
Модели и миграции меняет только Марк.

## Когда считаем MVP готовым

Для каждого пункта M01-M10 нужен результат проверки с датой, исполнителем и SHA.
Проверяем PostgreSQL, настоящего бота, качество 30 текстов и 20 аудио, доставку
30 напоминаний, нагрузку, восстановление и работу 5 внешних пользователей.

Потеря или раскрытие данных, неверный получатель, время без подтверждения
и неконтролируемый расход блокируют запуск. Если к сроку остаются незакрытые
пункты, можно проводить только ограниченный пилот с их явным перечнем.
