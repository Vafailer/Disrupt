# API статистики

Работа идёт в `feature/admin-api-v1`, поверх `feature/reminder-web-v1`.
Ветки не объединялись. Экран `admin.html/js/css` остаётся за основателем.
Его можно подключать к работающим методам, формат `AdminSummary` сохранён.

## Получить данные

`GET /admin-api/v1/summary` принимает `from` и `to` в формате `YYYY-MM-DD`.
Дни включаются целиком по Москве. Период не длиннее 366 дней,
конец не позже сегодняшнего дня. Ошибка фильтра возвращает 422.

`channel` принимает `all`, `web` или `telegram`. `source` по умолчанию равен
`all`. Источник берётся из первого привлечения в `User.source`, без известного
источника остаётся `unknown`. Сам API статистики не определяет источник по тексту
или последнему каналу пользователя.

Метод возвращает `cards`, `daily`, `funnel`, `retention`, `usage`, `quality`
и `generated_at`. Пример есть в [admin-summary.json](fixtures/admin-summary.json),
схема в [integration-v1.openapi.json](integration-v1.openapi.json).

Для usage есть `usage_limit=50`, допустимо от 1 до 100, и `usage_offset=0`.
Следующая страница указана в `X-Next-Usage-Offset`. На последней странице
заголовка нет. Строки идут от новых к старым, при равном времени по ID.
Карточки и расходы не зависят от пагинации.

`GET /admin-api/v1/export` принимает те же даты, канал и источник.
CSV содержит все карточки, дневные строки, воронку, удержание и качество.
Проценты развёрнуты в отдельные numerator, denominator и value.
Пустая ячейка означает null. Сырых usage и содержимого заметок в CSV нет.
В конце есть выбранные фильтры и время расчёта. Строки защищены от формул.

Нужна отдельная сессия администратора и доступ из приватной сети.
Без сессии ответ 401, снаружи сети 404. Обычный аккаунт и поле `users.role`
ничего не дают. Подробности и создание администратора в
[admin-security-v1.md](admin-security-v1.md). Старые пути `/api/admin/*` удалены.
JSON, CSV и ответы об ошибках получают `Cache-Control: no-store`.

## Как считаем

DAU включает сохранение записи, открытие результата, правку заметки,
подтверждение напоминания и выполнение задачи. Обработка, доставка,
вход и опрос статуса DAU не увеличивают. Один аккаунт в двух каналах
считается один раз. Сумма DAU каналов может быть больше общего DAU.
В `daily` есть каждый день, даже без активности.

`cards.dau` относится к последнему завершённому дню периода. Если выбран
только сегодняшний день, показывается наблюдаемый DAU. Время расчёта
есть в `generated_at`. Регистрации считаются по серверным событиям.
Старые аккаунты без событий регистрации не получают выдуманную дату.

`unique_users` считает активных людей за период. `new_users` и
`returning_users` делят их по первому входу. В дневных строках это деление
делается относительно самого дня, в карточках относительно всего периода.
Если дата первого входа неизвестна, она не придумывается для этого деления.
Поэтому один человек может быть новым в понедельник и вернувшимся во вторник,
но остаться новым в карточках за оба дня.

Когорта активации состоит из пользователей с первым входом в периоде.
Для выбранного канала нужны их человеческие события в этом же срезе.
Это включает вход и регистрацию, поэтому новый человек без записи тоже
попадает в знаменатель. Исторические тестовые события не создают когорту.
Через 24 часа от первого входа пользователь попадает в зрелый знаменатель.
До этого он виден в `activation_pending`, даже если уже выполнил сценарий.

ИИ-активация требует сохранения собственной AI-записи, открытия её результата
и проверки структуры или правки этой же заметки за первые 24 часа.
Ручная активация требует ручной записи, открытия и открытия через поиск
либо подтверждения напоминания для той же заметки. Канал и источник применяются
к каждому шагу. Действия с разными заметками не склеиваются.

`completed_scenario` считает людей, прошедших эти шаги в выбранном периоде,
без ограничения первым входом. `returns` требует отдельного открытия через
поиск или доставленное напоминание после активации. Первая ручная активация
через поиск сама по себе ещё не считается последующим возвратом.

Воронка начинается с когорты новых пользователей, её шаг `registered`
не равен карточке регистраций в канале. Например, аккаунт зарегистрирован
в вебе, а запись сохранена в Telegram. Остальные шаги проходят в порядке
сохранение, открытие, проверка структуры, последующий возврат.
Все шаги воронки лежат внутри выбранного периода. Conversion каждого шага
делится на размер начальной когорты. Активация может дозреть в свои 24 часа
после конца периода, поэтому она не обязана совпадать с воронкой.

D0 означает московский день первого входа. Для D1/D7 нужны активация в D0,
прошедшие 24 часа и целевое действие в нужный календарный день.
День проверки должен закончиться. Когорты без законченного дня показываются
в pending. Наблюдение за когортой продолжается за концом выбранного периода
до `generated_at`. Канал и источник сохраняются и для этих действий.

При нулевом знаменателе процент равен null. Пользователи с текущим
`User.is_test=true` исключаются вместе со всей историей. Снимки `is_test=true`
в событиях и usage тоже исключаются, даже после снятия флага аккаунта.

## Вызовы и расходы

Worker сохраняет квитанцию `ProviderUsage` перед отправкой каждой стадии.
У LLM и STT отдельные строки с одним ID задания. Повтор стадии не разрешён
уникальным `request_id`. До известного результата статус равен `unknown`.
Таймаут и остановка процесса не запускают повторный запрос.
Отказ до вызова, например отсутствие STT, не создаёт фиктивную квитанцию.

Квитанция относится к каналу и сессии исходной записи. Человеческая сессия
объединяет каналы при паузе не больше 30 минут. Фон её не продлевает.
В daily считается число сессий с человеческими событиями в этом дне,
в общих расходах число разных сессий за весь период. Одна сессия через полночь
может попасть в два дня, но в общем количестве останется одной.

Адаптер сохраняет только целые неотрицательные счётчики из ответа провайдера.
Отсутствующие или неверные input/output/cache tokens остаются null.
Счётчики сохраняются и при неправильной структуре ответа модели.
STT seconds означает длительность поданного оригинала, не подтверждённое
количество оплаченных секунд.

Стоимость в рублях передаётся десятичной строкой. Если хотя бы у одного вызова
нет измеренной стоимости, полный итог этого вида вызовов равен null.
Известная часть остаётся в `known_llm_cost` и `known_stt_cost`.
Оценка `estimated_cost` не заменяет измеренную стоимость.
`unknown_usage_calls` считает каждый вызов один раз, если неизвестна стоимость
или хотя бы один относящийся к нему счётчик. Полные токены тоже равны null,
если части данных нет. Нулевой итог допустим, когда вызовов не было.

`cost_per_user` делит полную стоимость LLM и STT на активных людей,
`cost_per_session` на человеческие сессии. `llm_cost_per_dau` делит только LLM
на сумму дневных DAU. При пустом знаменателе или неизвестной стоимости итог null.
Все числители и знаменатели используют один выбранный срез.

У встроенных mock-провайдеров нет обращения к платному сервису.
Их стоимость и оплаченные LLM tokens равны нулю, тариф `mock-no-billing-v1`.
Эти числа не показывают токенизацию текста настоящей моделью.
Живые тарифы и вычисление цены из tokens здесь не добавлены.

Для старых завершённых LLM-заданий и сохранённых STT-ревизий без квитанции
показывается `legacy-untracked` с неизвестной стоимостью. Дата такой строки
берётся из окончания задания или сохранения первой расшифровки. Это не дата
отправки запроса. Скрытые данные старого вызова восстановить нельзя.
Старые отказы до модели не считаются вызовами. При старом execution_unknown
или internal_error без квитанций показываются возможные незарегистрированные
стадии. Для аудио это STT и LLM, для текста LLM. Их счётчики означают возможные
попытки, а не подтверждённые обращения. Расход остаётся неизвестным. По старому
сбою нельзя доказать ни оплату, ни её отсутствие.

В качестве считаются результаты обработки, разные исправленные заметки
и p95 известных задержек от создания задания до завершения, включая очередь.
Для напоминаний учитывается последний известный результат каждой попытки
внутри периода. Retryable входит в failed. Поздний подтверждённый результат
заменяет unknown той же попытки. Старый reminder_failed без снимка результата
остаётся failed, точный статус для него не придумывается.

В ссылку напоминания добавлен `reminder`. При осознанном открытии веб передаёт
его в `/notes/{id}/opened`. Сервер проверяет владельца, заметку и доставку
sent/unknown, после чего записывает reminder_opened. GET и опрос задания
таких событий не создают.

## Псевдонимы и миграция

В usage нет текстов, аудио, имён, контактов и исходных ID аккаунтов или заданий.
ID квитанции, пользователя, сессии и операции заменены HMAC-псевдонимами.
Для стабильности между перезапусками задайте отдельный секрет не короче
32 символов через `NOTES_ANALYTICS_PSEUDONYM_KEY_FILE`.
Есть вариант `NOTES_ANALYTICS_PSEUDONYM_KEY`, одновременно задавать оба нельзя.
Секрет не связан с Cloud.ru, ботом или внутренним API. При смене секрета
псевдонимы меняются. Без настройки используется случайный ключ процесса.
Агрегаты от него не зависят, но страницы usage разных процессов не будут иметь
одинаковые псевдонимы. Это нужно учесть при развёртывании нескольких API.

Миграция `b17f03a29c64` идёт после `c7e921ab064f` и добавляет только
subject_id/outcome в события и is_test в usage. Старые события не дополняются
догадками. Старые серверные проверки с ID заметки ещё можно связать с записью,
а произвольный UUID старого открытия не позволяет узнать его заметку.
После обновления worker и API новые события уже содержат нужную связь.

В каждом запросе авторизация и расчёты используют один снимок базы.
Для PostgreSQL это REPEATABLE READ, для SQLite явная транзакция чтения.
JSON и CSV вызывают одну функцию расчёта. Два разных запроса могут отличаться,
если между ними появились события или дозрела когорта. Для сравнения смотрите
`generated_at`.

## Проверка

```sh
python -m alembic upgrade head
python -m alembic check
python -m ruff check app tests migrations scripts telegram_adapter
python -m pytest -q
PYTHONPATH=. python scripts/export_contract.py
```

Тесты используют синтетические записи, mock и подменённый HTTP.
Проверяются два канала одного человека, дубль события, оба варианта тестового
аккаунта, незрелая когорта, активация одной записи, D1/D7, полночь,
пауза сессии, доступ, смена роли, пагинация, CSV, квитанция до вызова,
ошибка структуры, таймаут, остановка worker и отдельные STT/LLM строки.
Есть проверка PostgreSQL через `TEST_POSTGRES_URL` только для локальной БД CI.
Ключ Cloud.ru не используется. Реальное STT, стоимость, экран админки
и приёмка на сервере остаются отдельными работами.

Полный локальный набор прошёл с 407 passed и 8 skipped. Пропущены только
проверки PostgreSQL, локального сервера нет. Ruff, миграция пустой SQLite,
alembic check, повторная генерация OpenAPI и три DOM-проверки веба прошли.
Результат CI для опубликованного SHA фиксируется в PR.
