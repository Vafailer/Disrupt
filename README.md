# Умные заметки

Мы делаем приложение, которое помогает записать мысль как есть, привести её в порядок и заметить возможные выводы. Оригинал остаётся у пользователя. Выводы ИИ показываются отдельно, их можно принять или отклонить.

Сейчас работает текстовый сценарий. Пользователь входит в аккаунт, отправляет запись, получает заметку с отдельными задачами и идеями, правит её и видит историю изменений. Задачу можно выполнить или вернуть в работу. Категории можно создавать и переименовывать. Поиск учитывает заголовок, исходник, обработанный текст и элементы записи. После проверки результата можно нажать «Структура верна».

Текст можно сохранить без ИИ. Тогда задание обработки не создаётся и запрос к модели не отправляется. Ручные записи тоже доступны в поиске, к ним можно добавлять задачи и категории. Поиск пока показывает готовые заметки и ручные записи. Исходники, для которых обработка ещё не завершилась или вернула ошибку, доступны в последних записях.

Есть привязка Telegram с подтверждением в вебе, внутренний API для приёма текста и обработки кнопки выполнения задачи. В вебе можно создать, изменить и отменить напоминание для заметки или открытой задачи. Пользователь выбирает точное время и часовой пояс, проверяет их и подтверждает. Конфликт сохраняет черновик, неизвестная отправка видна в списке. [Инструкция формы](docs/reminder-web-v1.md) описывает сценарий. Scheduler создаёт очередь, отдельная задача бота отправляет напоминания. [Инструкция доставки](docs/telegram-delivery-v1.md) описывает запуск и повторы. Связка проверена с подменённым Telegram, живую доставку ещё нужно проверить. PWA оставили на следующий этап после MVP.

Аудиомодуль коллеги подключён к приложению. В вебе можно загрузить файл или записать голос, прослушать и скачать оригинал, исправить расшифровку и открыть её историю. Поддерживаются Ogg/Opus, WAV/PCM и WebM/Opus до 10 МиБ и 180 секунд. Для проверки файлов нужны FFmpeg и FFprobe. Worker сохраняет первую расшифровку перед LLM. Реальное распознавание ещё не подключено. Без STT-провайдера задание получит `stt_not_configured`, оригинал останется доступным, текст можно вписать вручную. Сохранение правок не запускает модель. Подробности есть в [инструкции веба](docs/audio-web-v1.md).

Тексты заметок и голосовые записи хранятся зашифрованными (AES-256-GCM, ключ лежит в файле на сервере). Дамп базы или папка с аудио без ключа ничего не раскрывают. На production шифрование обязательно. Что шифруется, как создать и хранить ключ и как включить на сервере, написано в [инструкции](docs/encryption-v1.md). Потеря ключа означает потерю данных.

Распределение работы на четыре дня описано в [плане](docs/four-day-plan.md). Для бота и админки подготовлены [контракт API](docs/integration-v1.md) и [пример JSON](docs/fixtures/admin-summary.json). В полной OpenAPI будущие методы помечены `contract-only`. Схема работающих методов доступна в `/openapi.json`. Админка это отдельная учётная запись с паролем и кодом из приложения, доступная только из приватной сети, подробности в [админ-безопасность](docs/admin-security-v1.md). API агрегатов и CSV уже работают, [правила расчёта](docs/admin-api-v1.md) описаны отдельно. Экран админки остаётся за основателем.

По умолчанию приложение использует `mock` и не обращается к нейросети. Адаптер моделей проверен автоматическими тестами с подменёнными HTTP-ответами. Владелец ключа подтвердил, что модель отвечает в приложении. Качество ответов и фактический расход команда ещё не оценивала.

## Попробовать без API-ключа

На Windows откройте `start-demo.cmd` двойным щелчком. Если Python-окружения ещё нет, сначала выполните в PowerShell из корня репозитория:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\start-demo.cmd
```

Откройте `http://127.0.0.1:8000`. Зарегистрируйтесь, нажмите «Попробовать пример» и затем «Структурировать». Можно открыть исходный текст, изменить заметку и принять или отклонить вывод. После перезапуска данные останутся в `data/notes.db`. Окно сервера должно оставаться открытым; для остановки нажмите Ctrl+C.

Для произвольного текста `mock` сохраняет простую разметку без выводов. Это позволяет проверить работу приложения, но ничего не говорит о качестве настоящей модели.

На Linux или macOS запуск выглядит так:

```sh
python3.12 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
export NOTES_PROVIDER=mock
export NOTES_ALLOW_LIVE_REQUESTS=false
export NOTES_DATABASE_URL=sqlite:///./data/notes.db
.venv/bin/python -m alembic upgrade head
.venv/bin/python -m uvicorn app.main:create_app --factory --host 127.0.0.1 --port 8000
```

## Проверить с Cloud.ru

Владелец ключа может запустить `start-cloudru.cmd` на своём компьютере. Скрипт попросит ключ скрытым вводом, ID модели и общий лимит обращений. Запросы пойдут через шлюз Sber500, указанный в инструкции программы. По умолчанию лимит равен `5`. Это число запросов к модели за всё время существования отдельной базы `data/cloudru.db`, а не количество токенов или сумма в рублях. Уже занятые запросы не обнуляются после перезапуска. Этот режим использует отдельную базу приложения, поэтому после демо здесь нужно зарегистрироваться заново.

Не отправляйте ключ в чат и не добавляйте его в `.env` или Git. Скрипт не проверяет ключ при запуске. Первый запрос к модели произойдёт, когда вы отправите запись на обработку. Перед этим проверьте, что ID модели доступен вашему ключу. Подробности есть в [инструкции по Cloud.ru](docs/cloudru.md).

Если ответ модели содержит ошибку или неверный формат, исходная запись сохранится, а задание получит статус ошибки. Автоматических повторных обращений к модели нет. Ручной повтор с новым ключом идемпотентности может потратить ещё один запрос.

## Как устроен доступ к модели

Пользователю API-ключ Cloud.ru не нужен. Браузер отправляет текст нашему серверу. Сервер сохраняет запись и задание в базе, а отдельный worker обращается к модели и записывает результат. При серверном развёртывании секрет доступен только worker через Docker Secret. Подготовленная конфигурация с PostgreSQL и HTTPS описана в [инструкции по развёртыванию](docs/deployment.md).

Для локальной проверки PostgreSQL в Docker можно выполнить:

```sh
docker compose up --build
```

Это запускает API, PostgreSQL, worker и scheduler в режиме `mock`. Docker на машине разработки отсутствует. Конфигурацию и сборку образов проверяет CI, запуск всей системы на сервере ещё нужен.

## API и проверки

Документация API доступна по адресу `http://127.0.0.1:8000/docs`. Для запросов, которые меняют данные, нужны cookie сессии и `X-CSRF-Token` из ответа при входе или из `GET /api/v1/auth/me`. Swagger сам этот заголовок не подставляет.

Запись отправляется через `POST /api/v1/captures/text` с `Idempotency-Key`. Метод возвращает задание, состояние которого видно по `GET /api/v1/jobs/{id}`. Готовые заметки можно получить через `GET /api/v1/notes` и `GET /api/v1/notes/{id}`. Ручные правки и решения по выводам выполняются через `PATCH` с проверкой версии. Полный сценарий описан в [плане бэкенда](docs/backend-plan.md).

```powershell
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe -m ruff check app tests migrations
.\.venv\Scripts\python.exe -m alembic check
```

Тесты используют вымышленный ключ и подменённый HTTP-транспорт. Выданный команде лимитированный токен при разработке и проверках не используется. Результаты уже выполненных проверок записаны в [docs/verification.md](docs/verification.md).

При неожиданной ошибке API или сбое обработки приложение пишет запись в `data/errors.log`. Там есть время, код ошибки, место в коде и ID задания или запроса, по которому можно найти нужную запись. Текст заметки, ключ и сообщение исключения в лог не попадают. Файл ограничен 1 МБ, старые записи хранятся в трёх копиях. Путь можно изменить через `NOTES_ERROR_LOG_FILE`; пустое значение оставит только вывод в журнал процесса. На сервере ошибки также видны через `docker compose --env-file .env.production -f compose.production.yaml logs api worker`.
